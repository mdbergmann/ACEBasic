Struct Enhancements Specification
==================================

Date: 2026-02-15
Status: Draft


Overview
--------
Two language enhancements for ACE BASIC structs:

1. Allow arrays of any base type in struct definitions (not just STRING)
2. Fix and extend nested struct support (embedded access, typed pointers,
   self-references)


Current State
-------------
Struct members currently support these types:
  BYTE, SHORTINT, LONGINT, ADDRESS, SINGLE, STRING [SIZE n]

STRING SIZE n is the only way to declare a fixed-size buffer in a struct.
This is misleading because programmers expect STRING to mean string data,
but it is often used for raw byte buffers or flat arrays of records.

Nested struct members (using another struct name as type) are parsed and
stored correctly, but runtime access via chained -> does not work.


=======================================================================
PHASE 1: Typed arrays in structs (BYTE/SHORT/LONG/SINGLE SIZE n)
=======================================================================

Syntax
------
  STRUCT MyStruct
    BYTE buf SIZE 4096          ' 4096-byte buffer
    LONGINT values SIZE 10      ' array of 10 LONGINTs (40 bytes)
    SHORTINT flags SIZE 8       ' array of 8 SHORTINTs (16 bytes)
    SINGLE coords SIZE 3        ' array of 3 SINGLEs (12 bytes)
    STRING name SIZE 64         ' unchanged - still works
  END STRUCT

SIZE means element count (not byte count) for all types:
  BYTE buf SIZE 256      -> 256 bytes   (256 * 1)
  SHORTINT arr SIZE 10   -> 20 bytes    (10 * 2)
  LONGINT arr SIZE 10    -> 40 bytes    (10 * 4)
  SINGLE arr SIZE 10     -> 40 bytes    (10 * 4)
  STRING str SIZE 64     -> 64 bytes    (unchanged, already element=byte)

Access semantics: accessing an array member pushes its ADDRESS (same as
STRING members today). The caller uses PEEK/POKE or pointer arithmetic
for individual elements.

  DECLARE STRUCT MyStruct s
  addr& = @s->buf              ' address of byte buffer
  addr& = @s->values           ' address of LONGINT array
  POKEL addr& + 4, 42          ' set values(1) = 42

Future: indexed access s->values(i) could be added later.

Files to modify
---------------
1. declare.c - define_structure() lines 146-175
   Current: SIZE only accepted when mem_type == stringtype
   Change: Accept SIZE for bytetype, shorttype, longtype, singletype too

2. sym.c - add_struct_member() lines 755-767
   Current: Only stringtype and structure set strsize
   Change: For any type with SIZE, store element count in strsize,
   compute total bytes = count * element_size for struct size

3. declare.c - declare_structure() BSS emission lines 265-283
   Current: BYTE -> ds.b 1, SHORT -> ds.w 1, LONG -> ds.l 1
   Change: If member has strsize > 0 (array), emit ds.b/ds.w/ds.l count
   using strsize as the count

4. misc.c - push_struct() lines 283-376
   Current: BYTE/SHORT/LONG/SINGLE push a single scalar value
   Change: If member has strsize > 0 (array), push address instead
   (same codegen path as stringtype: adda.l #offset,a0 / move.l a0,-(sp))

5. assign.c - assign_to_struct()
   Current: BYTE/SHORT/LONG/SINGLE store a single scalar value
   Change: If member has strsize > 0 (array), treat as address assignment
   (prevents accidental scalar assign to array member)

Detail: STRUCM.strsize field reuse
-----------------------------------
Currently strsize is only set for stringtype and structure members.
For array members of other types, strsize will store the element count.
To distinguish "scalar with strsize=0" from "array with strsize=N":
  - strsize == 0  -> scalar member (current default)
  - strsize > 0   -> array member with N elements

The BSS emission and access codegen check strsize to decide whether
to emit a single slot or an array, and whether to push value or address.

Backward compatibility
----------------------
STRING SIZE n continues to work exactly as before. No existing code breaks.
BYTE/SHORT/LONG/SINGLE without SIZE continue to be scalars (strsize=0).

Alignment caveat (pre-existing, not introduced by this change)
--------------------------------------------------------------
ACE has NO automatic alignment padding between struct members. Offsets
are raw cumulative sizes. On the 68000, WORD and LONG accesses must be
at even addresses - a misaligned access causes a bus error (address
error exception).

This means:
  STRUCT Bad
    BYTE a                ' offset 0
    SHORTINT arr SIZE 10  ' offset 1 - MISALIGNED! 68000 bus error
  END STRUCT

  STRUCT Good
    BYTE a                ' offset 0
    BYTE _pad             ' offset 1 - manual padding
    SHORTINT arr SIZE 10  ' offset 2 - correctly aligned
  END STRUCT

This is the same constraint that already applies to scalar members:
  BYTE + SHORTINT or BYTE + LONGINT requires manual BYTE padding.
The AmigaOS system headers in include/ all use explicit padding BYTEs
(added by the ConvertC2ACE tool). User-defined structs must do the same
when mixing BYTE members with WORD/LONG-aligned types.

BYTE SIZE n arrays are unaffected (byte access has no alignment
requirement). LONGINT/SHORTINT/SINGLE SIZE n arrays follow the same
alignment rules as their scalar counterparts.


=======================================================================
PHASE 2: Fix embedded struct member access
=======================================================================

Problem
-------
Embedded struct members are defined correctly:
  STRUCT Inner
    LONGINT x
    LONGINT y
  END STRUCT

  STRUCT Outer
    Inner pt
    LONGINT z
  END STRUCT

The parser stores pt as type=structure with correct offset and size.
BSS emission allocates the right number of bytes.

But accessing outer->pt falls through to the generic LONG push path
in push_struct() (misc.c:355), which reads 4 bytes as a LONGINT.
This is wrong - an embedded struct is larger than 4 bytes.

Accessing outer->pt should either:
  a) Push the ADDRESS of the embedded data (if no further ->)
  b) Chain into the nested struct (if followed by another ->)

Chained access: outer->pt->x should work and resolve to the correct
offset (pt.offset + x.offset from struct base).

Files to modify
---------------
1. misc.c - push_struct() ~line 354
   Add case for mbr_type == structure:
   - Compute address: adda.l #member_offset, a0
   - If next token is memberpointer (->):
     * Get nested structdef from member's structtype link
     * Parse next member name
     * Look up in nested structdef's member list
     * Apply nested offset from a0
     * Push value (or recurse for deeper nesting)
   - If no further ->:
     * Push address of embedded struct: move.l a0,-(sp)
     * Return longtype (it's an address)

2. assign.c - assign_to_struct()
   Same logic: support chained -> for nested struct assignment.
   outer->pt->x = 5 must resolve the full offset chain.

3. sym.c - STRUCM struct
   Need a way to find the nested structdef from a struct member.
   Option A: Add a SYM *structdef pointer to STRUCM (cleanest)
   Option B: Look up the struct type by scanning structdefs by size
   (fragile - multiple structs could have the same size)

   Recommend Option A: add field to STRUCM in acedef.h:
     typedef struct structmem {
       char  name[MAXIDSIZE];
       int   type;
       ULONG offset;
       ULONG strsize;
       SYM   *structdef;     /* NEW: for type=structure, points to def */
       struct structmem *next;
     } STRUCM;

   Set in add_struct_member() when mtype == structure:
     curr_structmem->structdef = structtype;

Detail: recursive chaining
--------------------------
For deeply nested structs (a->b->c->d), the resolution loop in
push_struct can iterate rather than recurse:

  /* initial: a0 = base address of outermost struct */
  while (next_sym == memberpointer) {
    add offset of current member to a0
    look up next member in current member's structdef
    update current member
  }
  /* final member: push value or address depending on type */

This avoids deep recursion and handles arbitrary nesting depth.


=======================================================================
PHASE 3: Typed struct pointers as members
=======================================================================

Syntax
------
  STRUCT Container
    Inner embedded         ' embedded struct (Phase 2)
    Inner *ptr             ' NEW: typed pointer to Inner (4 bytes)
  END STRUCT

Inner *ptr stores an ADDRESS (4 bytes in BSS) but the compiler knows
it points to an Inner struct, enabling -> chaining through the pointer.

  DECLARE STRUCT Container c
  c->ptr = ALLOC(SIZEOF(Inner))    ' allocate an Inner
  c->ptr->x = 5                    ' access through typed pointer

vs. current:
  ADDRESS ptr                       ' untyped, no chaining possible

Files to modify
---------------
1. declare.c - define_structure() ~line 116
   After matching a struct name as member type, check for * token.
   If present:
     - mem_type = longtype (stored as 4-byte pointer)
     - Record the pointed-to structdef in STRUCM.structdef
     - Mark as pointer (new flag in STRUCM, or a new type like structptrtype)

2. acedef.h
   Option A: Add structptrtype to type enum
   Option B: Add a BOOL is_pointer field to STRUCM
   Recommend Option A for cleaner type dispatch in codegen.

3. sym.c - add_struct_member()
   For structptrtype: size += 4 (pointer), store structdef reference.

4. declare.c - declare_structure() BSS emission
   For structptrtype: ds.l 1 (just a pointer slot).

5. misc.c - push_struct()
   For structptrtype member:
   - Load the pointer value: move.l offset(a0),a0
   - If followed by ->: resolve nested member from structdef
   - If no ->: push pointer value as LONGINT

6. assign.c - assign_to_struct()
   For structptrtype member:
   - Without ->: assign address value (move.l to offset)
   - With ->: dereference pointer, then assign to nested member


=======================================================================
PHASE 4: Self-referential structs
=======================================================================

Syntax
------
  STRUCT Node
    Node *next             ' pointer to self (4 bytes)
    LONGINT value
  END STRUCT

Currently blocked by declare.c line 118:
  if (!exist(id,structdef) || strcmp(id,structdef_item->name) == 0)
      _error(65);

This rejects using the struct's own name during its definition.

Fix
---
Relax the check: only reject self-reference for EMBEDDED (non-pointer)
members, since an embedded self-reference would be infinite size.
Self-referential POINTERS are fine (always 4 bytes).

  if (!exist(id,structdef))
      _error(65);                    /* unknown struct type */
  else if (strcmp(id,structdef_item->name) == 0)
  {
      /* self-reference: only allowed as pointer */
      insymbol();  /* peek at next token */
      if (sym != multiply)
          _error(65);  /* embedded self-ref = infinite size */
      /* else: continue, will be parsed as pointer in Phase 3 */
  }

Dependency: Requires Phase 3 (typed struct pointers) to be useful.


=======================================================================
PHASE 5: Struct arrays as struct members (SIZE on struct-typed members)
=======================================================================

Syntax
------
  STRUCT Inner
    LONGINT x
    LONGINT y
  END STRUCT

  STRUCT Container
    Inner items SIZE 10         ' 10 embedded Inner structs
    LONGINT count
  END STRUCT

items occupies 10 * sizeof(Inner) = 80 bytes in BSS, laid out
contiguously as 10 Inner instances.

Access: indexed with parentheses, then chained with ->:
  DECLARE STRUCT Container c
  c->items(3)->x = 42          ' items_offset + 3*sizeof(Inner) + x_offset
  val = c->items(0)->y

Without index, c->items pushes the base address of the array
(same as other array members).

Files to modify
---------------
1. declare.c - define_structure() ~line 146
   Extend the SIZE check to also accept mem_type == structure.
   Already handles stringtype; structure with SIZE is analogous.

2. sym.c - add_struct_member()
   For structure with SIZE: total bytes = count * structtype->size.
   Store count in strsize (or a dedicated arraycount field).
   Store structtype in STRUCM.structdef (from Phase 2).

3. declare.c - declare_structure() BSS emission
   For structure members with strsize > single struct size:
     ltoa(strsize, ...) already works (strsize = count * struct_size).
   No change needed - the existing stringtype/structure BSS path
   emits ds.b <strsize> which covers the full array.

4. misc.c - push_struct()
   For structure member with array count > 1:
   - Parse (index) after member name
   - Compute element offset: member->offset + index * element_size
     where element_size = member->structdef->size
   - Add to a0, then check for -> to resolve nested member
   - Without further ->: push address of indexed element
   Code generation:
     adda.l #member_offset, a0       ' base of array
     ' index computation (if constant: immediate add, else multiply)
     move.l <index>, d0
     mulu #element_size, d0          ' or muls for signed
     adda.l d0, a0                   ' a0 = &items[index]
     ' then resolve ->field if present

5. assign.c - assign_to_struct()
   Same indexed access logic for the left-hand side of assignment.

Element size for index computation
----------------------------------
The element size comes from member->structdef->size (set in Phase 2).
For constant indices, the compiler can fold index * element_size into
a single immediate offset at compile time (optimization, not required).

For variable indices, the generated code uses mulu (unsigned multiply)
since struct sizes and indices are non-negative. If the index is a
LONGINT expression, it must be evaluated and left on the stack, then
popped into d0 for the multiply.

Bounds checking
---------------
Optional. If desired, the compiler could emit a runtime check:
  cmp.l #count, d0
  bcc _struct_bounds_error
This is a future enhancement, not required for Phase 5.

Dependency: Requires Phase 2 (STRUCM.structdef pointer and chained
-> resolution).

Relation to Phase 1
--------------------
Phase 1 adds SIZE for base types (BYTE, SHORT, LONG, SINGLE).
Phase 5 adds SIZE for struct-typed members. Both use the same SIZE
keyword and similar codegen patterns. They could be implemented
together or separately. Phase 5 additionally needs indexed access
codegen with multiply, which base-type arrays would also benefit
from in a future enhancement (e.g. s->longArr(i)).


=======================================================================
Implementation Order
=======================================================================

Phase 1: BYTE/SHORT/LONG/SINGLE SIZE n       ~40 lines changed
         Solves the STRING naming issue and adds typed arrays.
         No dependencies. Fully backward compatible.

Phase 2: Fix embedded struct -> access        ~60 lines changed
         Makes existing embedded struct members actually usable.
         Requires adding structdef pointer to STRUCM.

Phase 3: Typed struct pointers (Inner *ptr)   ~50 lines changed
         Enables -> chaining through pointer members.
         Requires Phase 2 (shares the chaining codegen).

Phase 4: Self-referential structs             ~10 lines changed
         Allows linked lists, trees, etc.
         Requires Phase 3.

Phase 5: Struct arrays (Inner items SIZE n)   ~60 lines changed
         Arrays of structs as struct members with indexed access.
         Requires Phase 2 (structdef pointer, chaining).

Each phase should be implemented and tested in a separate branch.
